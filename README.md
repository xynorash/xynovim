# xynovim (formerly xyno-neovim)

Personal Neovim config, built on [LazyVim](https://github.com/LazyVim/LazyVim), running on Linux (Omarchy/Arch). The previous from-scratch Windows config lives on the [`windows-legacy`](../../tree/windows-legacy) branch.

Every notable change is documented in [CHANGELOG.md](CHANGELOG.md), including what was verified and how.

## What's here beyond stock LazyVim

### Rust

- **LazyVim `lang.rust` extra**: rustaceanvim + rust-analyzer, crates.nvim for Cargo.toml, codelldb for debugging, neotest adapter.
- **Two-tier diagnostics** for instant feedback with clippy depth:
  - *Instant tier (~0.01-0.15s measured, warm)*: rust-analyzer's native in-memory diagnostics, as you type, no cargo run involved. In practice that is type errors (E0308 mismatches) and the like. **Unresolved names, methods, types and imports (E0425, E0599, E0432) come from the depth tier** (about 0.6s later): rust-analyzer only reports them with `diagnostics.experimental.enable`, and that was measured to be unusable here (see below), so it stays off.
  - *Depth tier (~0.56s median, warm)*: clippy via [bacon-ls](https://github.com/crisidev/bacon-ls)'s native cargo backend (`lua/plugins/bacon-ls.lua`) with `updateOnInsert` — it mirrors the workspace into a hardlinked shadow under `target/bacon-ls-live/` and re-runs clippy (`--workspace --all-features --no-deps`, 500ms debounce) on every buffer change, before any save. `checkOnSave` is deliberately **off**: with ~1s auto-save it was a second cargo pipeline racing the live one — runs cancelled each other and serialized on cargo's build-dir lock (measured 5.6s edit-to-diagnostic with both pipelines vs single-pipeline sub-second). `updateOnInsert` must stay **on**: without it bacon-ls advertises no document sync and diagnostics never refresh.
  - The only overlap is visual: a type error can briefly show from both sources.
  - **`diagnostics.experimental.enable` stays off**: measured on a copy of a real 196-file axum/sqlx workspace that builds cleanly (rust-analyzer idle, one sweep per setting, 1.2s per file): off gives 0 rust-analyzer diagnostics, on gives 82 false errors (74 `E0282 type annotations needed`, 8 `E0277` axum `Handler` / `IntoFuture` bounds not satisfied) plus 6 inactive-`#[cfg]` hints. On a small std-only crate it did surface E0425/E0599/E0432 in 0.01-0.15s, so the trade is real, but not at that false-positive rate.
- **bacon-ls fixes are upstream** (Mason's bacon-ls >= 0.31.0; the earlier local patched build and its `cmd` override are gone). The three fixes behind the previous patch landed as [crisidev/bacon-ls#139](https://github.com/crisidev/bacon-ls/pull/139): (1) the debounce task drops its own handle once its sleep is over, so a later `abort()` can only cancel a still-sleeping trigger and in-flight runs are superseded via `CancelRunning` (progress tokens close properly); (2) with `checkOnSave` off, `didSave` no longer cancels a still-pending live trigger; (3) closing a dirty buffer clears its orphaned diagnostics and restores the shadow file by *copy* (fresh mtime), so cargo re-checks instead of replaying cached warnings.
- **rustaceanvim tuning** (`lua/plugins/rustaceanvim.lua`): inlay hints (closure return types, elided lifetimes), fill-arguments completion snippets, full function signatures, module-grouped auto-imports, and `cargo.targetDir = true` so rust-analyzer's build-script runs never contend for the build-dir lock with terminal `cargo run`/`cargo test`.
- **System-level build speed** (`~/.cargo/config.toml`, outside this repo): mold linker via clang (links several times faster — every clippy/test/run cycle benefits) and `profile.dev.debug = true` (full debuginfo: required for the debugger's Local scope; `line-tables-only` and `limited` show no locals). The user-level `[profile]` overrides a project's `Cargo.toml`, so per-project advice does not work: a project can only change it via its own `.cargo/config.toml` or `CARGO_PROFILE_DEV_DEBUG`. Do not use `split-debuginfo`: unpacked and packed both left codelldb without locals. Measured cost of `true` vs `line-tables-only` (two fixtures, single noisy runs): clean build about +14%, `target/debug` about +28%, incremental rebuild about +10%, clippy rerun unchanged.
- **bacon-ls roots at the Cargo workspace** (`lua/plugins/bacon-ls.lua`): a `root_dir` function returns the outermost `Cargo.toml` with a `[workspace]` table (`config.rust_context.root`), else the crate itself. The old nearest-`Cargo.toml` root made the shadow hold only the member, so cargo failed ("believes it's in a workspace when it's not"), no clippy diagnostics ever arrived and one client with its own `target/` started per opened member. No client for a standalone `.rs` file without a crate (it spammed cargo errors; rust-analyzer's detached-file mode is a separate client and still answers), nor for files under `~/.cargo/registry`, `~/.cargo/git` and `~/.rustup` (what `gd` into a dependency or std opens: each ships its own `Cargo.toml`, and a client there compiled the registry sources and wrote `target/` into `~/.cargo`). Verified headless on a 2-member workspace opened from a member (`app`, depending on `../pm`): exactly one client rooted at the workspace, still one after opening `pm`, a `len_zero` clippy warning arrived, no `target/` in the member; a `gd`-style registry buffer got rust-analyzer only. Not verified: a workspace with `exclude`d crates, nested workspaces, `rust-project.json` projects.
- **Server supervision** (`lua/config/rust_restart.lua`, `lua/config/lsp_status.lua`): a rust-analyzer or bacon-ls that dies (`kill -9`, OOM, crash) used to stay dead (`:RustAnalyzer restart` / `:lsp restart` need a live client). Now the statusline shows `RA stopped` / `clippy stopped` and the server is restarted automatically after 0.5s, at most 3 times a minute (then it gives up with an error); `:RustRestart` restarts both by hand, also when one is dead. A graceful exit (`:lsp restart`, quitting) is left alone. `clippy failed` replaces the false `clippy ok` when cargo cannot run at all (broken manifest, cyclic dependency): bacon-ls ends such a run normally and only sends an error `window/showMessage`; it clears on the next run. `clippy stale` now counts text changes (`nvim_buf_attach`) instead of `TextChanged`, because it stayed up for good after an auto-save while typing (`:write` bumps `b:changedtick` too; the fix was checked by typing with auto-save on and watching the status settle on `clippy ok`). **External changes**: bacon-ls hardlinks the workspace into its shadow once and re-syncs only the files nvim reports, so `sed -i`, `git checkout`/`pull` or an agent rewriting files left clippy checking the old content. On `FocusGained` (debounced 300ms) bacon-ls is restarted when a `.rs`/`.toml`/`.lock` buffer under its workspace was reloaded from disk (`checktime` + `FileChangedShellPost`) or the workspace's git HEAD moved; files that are not open in nvim and change without a HEAD move (a bare `sed -i` on an unopened file) are not noticed, `:RustRestart` or `:lsp restart bacon_ls` covers those. bacon-ls clients whose workspace directory no longer exists are stopped at the same time (a deleted crate leaked its client). Verified headless (real servers, as the user): `kill -9` of both servers gave `RA stopped | clippy stopped`, both back with new pids and `RA ready | clippy ok`, clippy diagnostics from the new bacon-ls; four quick kills ended at `clippy stopped` (loop guard) and `:RustRestart` revived it; a broken manifest gave `clippy failed`, repairing it `clippy ok`; `sed -i` on the open file then `FocusGained` restarted bacon-ls and the new error appeared; a commit (HEAD move) restarted it, no change did not; a copied crate directory deleted under a live client lost that client on `FocusGained`. Not verified: a real focus event in a terminal (`FocusGained` was fired with `:doautocmd`), a dirty buffer during the restart (upstream: bacon-ls writes buffer text to its shadow only on `didChange`, so an unsaved error shows again with the next edit), a server killed with `SIGTERM` (treated like a graceful stop only when it exits 0 and signal 0; a signalled exit restarts).
- **Debugger** (`lua/plugins/dap.lua`): the Rust configs "LLDB: Launch" and "LLDB: Launch (args)" now prompt with a default of `<cargo target_directory>/debug/<bin>` (bin from `cargo metadata`: the package holding the buffer, else the root package, else the first with a bin); new config "Rust: run current package binary (args prompt)" builds (`cargo build --package P --bin B`, non-blocking) and launches in the package directory. The dap-ui left sidebar is wider (35% of columns, clamped to 40..60) and wraps, with Scopes at 40% of its height, so long types such as `alloc::vec::Vec<alloc::string::String, alloc::alloc::Global>` stay readable. `<leader>dR` is the whole-workspace variant of `<leader>dr`: it lists bin and example targets from `cargo metadata` plus the current file's rust-analyzer runnables (`<leader>dr` from `lib.rs` lists only that file's tests). Verified headless and in tmux: the default path prints right, the new config stops at a breakpoint in `main` with locals shown, `<leader>dR` lists and starts the bin. Not verified: the interactive prompts (stubbed), multi-bin workspaces, very narrow terminals. `<leader>dR` uses rustaceanvim internals (`rustaceanvim.dap.start` and others) that an update could break; its request is silently dropped if the buffer has no rust-analyzer client yet.
  - **Formatters and panics** (batch 1): every Rust codelldb launch (the three configs, `<leader>dr`, `<leader>dR`) gets `sourceLanguages = {"rust"}`, an `initCommands` import of `<rustc sysroot>/lib/rustlib/etc/lldb_lookup.py` (String, Vec, Option and enums show as `"hello"`, `size=4`, `B(7)` instead of `{...}`; configs 1-3 lacked it, only `dr`/`dR` had it) and `breakpoint set -n rust_panic`, so a panic stops at the panicking frame instead of the session ending with exit 101 (a `#[should_panic]` test stops there too). Added in an nvim-dap `on_config` listener because rustaceanvim overwrites `initCommands` on its own launches; the unconditional `command source .../lldb_commands` is deliberately not used (the file does not exist on this toolchain). `<leader>dR` no longer drops per-test entries (its dedupe key ignored `executableArgs`; labels now read `... -- tests::t_one --exact ...`). `dap.autoload_configurations = false` (set in `init`, LazyVim's rust extra overwrites `opts.dap`): the upstream default ran `cargo test --no-run --all-targets` on every rust-analyzer attach (up to 5 at once in the field test), competing with your own cargo for the build-dir lock; `<leader>dr`, `<leader>dR` and `:RustLsp debuggables` ask rust-analyzer on demand and still work. nvim-dap is now a dependency of rustaceanvim (loaded with the first Rust buffer, +5ms measured: 150 vs 145ms to open a Rust file headless), because rustaceanvim only advertises `rust-analyzer.debugSingle` when dap is already loaded as the client is created: the "Debug" codelens was missing. Verified headless against codelldb on a crate whose `check()` panics: configs 1 and 3, `<leader>dr` and `<leader>dR` all stop in `__rustc::rust_panic` with `owned "hello"`, `v size=4`, `k B(7)` in the `check` frame; `<leader>dR` lists the per-test entries; no `cargo` child of nvim after attach; the codeLens resolve returned `rust-analyzer.debugSingle`. Not verified: clicking a Debug lens in a UI, tests that panic inside a spawned thread, `lldb-dap` instead of codelldb.

Requires: `rust-analyzer` on PATH; `bacon-ls` >= 0.31.0 from Mason (`:Mason`); `mold` + `clang` (pacman). The `bacon` binary is **not** needed by the cargo backend (it runs cargo/clippy directly); it's only used by the unused `backend = "bacon"` fallback in `~/.config/bacon/prefs.toml`.

### 99 (AI assistant)

[ThePrimeagen/99](https://github.com/ThePrimeagen/99) on the Claude Code provider (`lua/plugins/ninety-nine.lua`), model `claude-sonnet-5` with `--effort medium`.

Hard-won configuration notes:

- `tmp_dir` **must be an absolute path** (here: `~/.cache/nvim/99`). 99 resolves a relative tmp_dir against nvim's cwd, but claude resolves the same relative TEMP_FILE against the project it's working in — launch nvim from outside the project and every response comes back empty because the answer lands where 99 never reads.
- The logger needs `type = "file"` for `path` to take effect; the plugin README's example omits it and logs silently go nowhere. Logs land at `~/.local/state/nvim/99.log` (see step 5).
- The blink completion source (`#rules` / `@files` in the prompt buffer) needs `saghen/blink.compat`.

### Editor behavior

- **auto-save** (`lua/plugins/auto-save.lua`): okuuva/auto-save.nvim, ~1s debounce including while typing (`TextChangedI`). Autosaves skip format-on-save via `noautocmd`; a `User AutoSaveWritePost` hook re-sends `textDocument/didSave` so LSP save-triggered behavior survives. Manual `:w` still formats. Guards (`lua/config/disk_guard.lua`): it never writes into dependency/std sources (`~/.cargo/registry`, `~/.cargo/git`, `~/.rustup` buffers are `nomodifiable`; `:set modifiable` to edit one on purpose) and never over a file that changed on disk (the disk mtime recorded at read/write time is compared before the save and again right before the write; on a mismatch the save is skipped and one warning says `:w!` keeps the buffer, `:e!` takes the disk version; nvim's blocking W12 "Do you really want to write to it (y/n)?" used to swallow keystrokes). `FileChangedShell` never prompts (unmodified buffers reload, modified ones keep their edits), and LazyVim's `FocusGained` `:checktime` still runs. A workspace edit that touches other files (multi-file rename, file rename, code actions) is followed by a write of every modified buffer that passes the same check, so those files no longer stay unsaved. While a neotest watcher exists (`<leader>tw`), each autosave re-emits `BufWritePost` so the watcher reruns the tests (otherwise it is not emitted).
- **harpoon** (`<leader>H` adds a file, `<C-e>` menu, `<M-1..4>` jump; `<leader>a` is only the `claudecode` AI prefix), and desktop integration: transparency (re-applied on every `ColorScheme` change, toggle `<leader>uO`), the Omarchy theme hot-reload (now re-applies Island Dark, see Theme) and remote clipboard (OSC52, activates only under tmux/SSH/herdr).
- Format-on-save off globally (`vim.g.autoformat = false`), relative numbers off.
- **Editing and UI** (batch 4): `lua/plugins/editing-ui.lua`, `lua/config/ux.lua`, `after/ftplugin/rust.lua`.
  - `'` is typed plainly in Rust buffers (mini.pairs paired it after `&` and `<`, so `&'a str)` became `&'a str')`); a char literal's closing quote is one more key.
  - Spell checking in Rust comments and doc comments (`spell` plus `spelloptions+=camel`; only the treesitter `@spell` captures are checked, so identifiers and strings are skipped).
  - Diagnostic virtual text shows the first line plus `[source]` (clippy sends the whole rendered message, about 14 lines). A problem both tiers report on the same line (same rustc `E` code, else the same first line) is shown once, preferring rust-analyzer's text; the buffer's virtual text is redrawn when the other tier's diagnostics arrive or go. `<leader>cd` still shows the full message.
  - blink.cmp snippets are hidden after a `.` and inside strings and comments (friendly-snippets' `if` outranked rust-analyzer's `.if` postfix).
  - `winborder = "rounded"` (floats had no edge: solid `NormalFloat` on a transparent editor), noice's hover and signature help use the same border, `pumblend = 0` (LazyVim's 10 made buffer text show through the right-click menu), the coverage summary float is opaque and 60% x 40% of the screen.
  - The dashboard puts its entries on consecutive lines below 36 rows (at 80x24 the last entries and the footer were cut off); the statusline showcmd (pending keys) clears (noice kept the last one); `<leader>9` is named in which-key; the 99 model picker lists `claude-sonnet-5` (the provider's list is static).
  - taplo gets the Cargo.toml schema from schemastore (`edtion = ...` is reported, hover and completion know the keys) and `Cargo.toml` as a root marker. Not silenced: taplo 0.10.0's "failed to fetch catalog" line in `lsp.log` (it fetches before it reads settings).
  - sqlx injection: multi-line strings (`[[:space:]]` instead of `\s`) and more statement keywords (explain, vacuum, analyze, set, show, ...); the keyword must be a whole word.
  - cargo-machete findings are no longer doubled, cargo-deny `wildcard` lands on the dependency's line in `Cargo.toml` (label coordinates, so a wildcard of another workspace member can land on a wrong line) and is skipped on `Cargo.lock`; lazy's `rocks` is off (`:checkhealth lazy` no longer errors about luarocks).
  - Known: a Rust file over 1.5 MB gets Snacks' bigfile treatment (no LSP, only a notification); raise `opts.bigfile.size` for snacks.nvim if you need it. wgsl-analyzer's "Project discovery failed" is still not fixable from here (see roadmap step 10). `<leader>uC` previews of light themes leak `background=light` until a colourscheme resets it; Island Dark sets it back to dark.

### Theme

**Island Dark** is the permanent colourscheme (`:colorscheme island-dark`, `vim.g.colors_name == "island-dark"`). It is the user's own JetBrains "Island" dark scheme (scheme name `Dark`, parent Darcula, exported from RustRover 2026.2.3), kept in the repo as `tools/Dark.icls`.

- **Generated, not hand-copied**: `python3 tools/icls2nvim.py` (stdlib only) parses the `.icls` (colours, foreground/background, bold/italic, underline/undercurl/dotted effects, `baseAttributes` inheritance with the `DEFAULT_*` fallbacks) and writes `lua/island/palette.lua` (generated, do not edit). `lua/island/init.lua` maps that palette to editor UI, classic syntax groups, the Treesitter captures, LSP semantic tokens (`@lsp.type/mod/typemod`, incl. the scheme's `org.rust.*` colours) and the plugins in use (blink.cmp, snacks, which-key, neo-tree, trouble, gitsigns, diffview, dap/dap-ui, neotest, satellite, treesitter-context, navic, flash, noice, mini, harpoon, render-markdown, coverage, inlay hints, codelens); `colors/island-dark.lua` is the entry point and `lua/lualine/themes/island-dark.lua` the statusline theme. Only scheme colours are used. To change the colours, replace `tools/Dark.icls` and rerun the script (a restart picks up the new palette).
- **Derived (not in the export)**: the file has no selection colour, so `Visual`/`PmenuSel` use its blue `VCS_ANNOTATIONS_COLOR_2` (`#2d416b`); borders use `SELECTED_INDENT_GUIDE`. It has no `org.rust.LIFETIME` or trait entry: lifetimes use the type-parameter colour, traits the struct colour. `org.rust.UNSAFE_CODE` (a background band) is not applied: unsafe code keeps the underline from `plugin/after/unsafe-highlight.lua`. rust-analyzer's inactive `#[cfg]` code is a normal "unnecessary" diagnostic, so it shares the dim `NOT_USED` grey instead of the olive `CFG_DISABLED_CODE` (`RustCfgDisabled` holds that colour).
- **Transparency** stays the default: only the editor surface (Normal, gutter, line numbers, neo-tree) is transparent. Floats, the completion menu and which-key/telescope keep the solid popup background `#2b2d30` so they stay readable over code (`plugin/after/transparency.lua`). `<leader>uO` toggles the editor background; off gives the scheme's solid `#1e1f22`. `vim.g.xynovim_transparent = false` starts solid.
- **Legibility lifts (deviations from the export)**, from a contrast review (WCAG ratios computed from the loaded highlight groups, targets 4.5:1 body / 3:1 secondary): comments (`#7a7e85`, 4.0:1) and doc comments (`#5f826b`, 3.8:1) are mixed towards white just far enough to reach 4.5:1 (`#82868c`, `#6f8f7a`; the scheme has no lighter colour of that hue); error virtual text and floating error text likewise (`#f86574`/`#f8606f`, 4.5:1); line numbers use `WHITESPACES` `#6f737a` (3.5:1, scheme `#4b5059` is 2.0:1); blink.cmp detail/description/kind/source, Pmenu kind/extra, inactive statusline and picker paths use the `sub` grey `#9da0a8` (3.9:1 on the selected row); git "modified" uses `FILESTATUS_MODIFIED` `#70aeff` (7.2:1) instead of `#375fad` (2.7:1); the cursorline uses `VCS_ANNOTATIONS_COLOR_4` `#242d42` (1.20:1 on the background, the scheme's `#26282e` is 1.12:1) and `CursorLineNr` keeps its background so the band has no gap. `lift()` in `lua/island/init.lua` does the mixing. After `:colorscheme <other>` the lualine theme falls back to `auto`.
- **Omarchy**: its theme spec (`lua/plugins/theme.lua`, a symlink managed by Omarchy) is answered with an empty spec in `lua/config/lazy.lua`, and the `LazyReload` hot-reload in `omarchy-theme-hotreload.lua` re-applies Island Dark instead of Omarchy's colorscheme. The files and `all-themes.lua` stay, so to follow Omarchy again put `vim.g.xynovim_follow_omarchy = true` in `lua/config/options.lua`.
- **Verified**: headless, with the repo config: the colourscheme loads with no messages, `colors_name` is `island-dark`, 49 group/attribute checks against an independent parse of the `.icls` (colours, italic, underline) pass; on a scratch crate with the real rust-analyzer, struct, enum, enum variant, trait, macro, lifetime, static, const, `self`, derive/attribute, doc comment, `mut` binding, unsafe call/keyword and builtin type tokens resolve to the scheme colours; `:colorscheme tokyonight` and back, a simulated `User LazyReload`, the transparency toggle (real mapping), colourblind diagnostics and the unsafe underline survive; follow-Omarchy mode tested with a stand-in theme spec (catppuccin); startup about 1-2 ms slower than before (median 26.4 vs 24.5 ms headless, the colourscheme itself 2.3 ms). In tmux at 200x55 (24-bit colour): the SGR colours of Rust code, the completion menu, snacks picker, which-key, neo-tree, a diagnostic float, git signs, inlay hints and the statusline match the palette, solid mode paints `#1e1f22`.
- **Not verified**: a real Omarchy theme switch (no Omarchy here; only the `LazyReload` event was simulated), the look on other terminals or with their own background, plugins whose groups are defined from knowledge of their docs but were not on screen (trouble, diffview, dap-ui, neotest, satellite, render-markdown, flash, mini.* beyond MiniIcons), and `Failed to load` cases with a live Omarchy symlink. Known gaps: the cursorline is still a subtle band (1.20:1, by design); `PmenuMatchSel` is 4.0:1; the ratios assume the `#1e1f22` background, so a terminal with another background changes them. Contrast re-checked headless in both transparency modes and in tmux at 200x55 (cursorline, solid float, error virtual text SGR backgrounds); not re-checked: the blink.cmp menu itself on screen (the groups were measured, no completion was triggered).

### Performance choices

- ~35ms startup on 2026-10-12 (10 runs of `nvim --headless --startuptime`: 32.7 to 39.0 ms, mean 35.9; 80 plugins per lazy stats; earlier README figures of 25ms were from a quieter moment, the unfixed live config measures the same 33 to 36 ms today, so this is not a regression from the field-test fixes): 99 + blink.compat and harpoon lazy-load on their keymaps, and telescope too (`lua/plugins/telescope.lua` sets `lazy = true`: as a dependency-only plugin lazy.nvim otherwise loaded it at startup); the herdr `/proc` ancestry walk short-circuits behind env checks.
- lazy.nvim's periodic update checker is **off** (it re-fetched all plugin repos in the background and dragged `lazy.manage` into every startup) — update with `:Lazy sync`.
- Remote-plugin providers (python3/ruby/perl/node) disabled — nothing uses them.
- 99's request cache (`~/.cache/nvim/99`) is pruned of week-old files on load.

## Roadmap: closing the gap with RustRover

Result of a gap analysis against RustRover 2026.2 (researched 2026-10-08: 15 dimensions, each adversarially verified). xynovim already matches or beats RustRover on diagnostics latency, startup/footprint, raw rust-analyzer access and scriptability; the gaps below are mostly **tooling that is installed but inert** or unbound. Steps are in recommended order; each is verifiable (`:checkhealth`, a headless `nvim --headless` smoke run, or one real crate). Items marked *(unverified)* come from research that was not tested on this machine; test them before building on them.

### 1. Reality check: done 2026-10-09
Findings on this machine and what was done:
- `~/.cargo/bin/bacon-ls` and `~/.local/src/bacon-ls-upstream` did not exist, so the `cmd` override pointed at nothing and the clippy tier was dead. #139 is merged (2026-09-10) and shipped in 0.31.0 (2026-09-20); Mason has 0.31.0 (0.32.0 is the latest upstream). **Fixed:** removed the override in `lua/plugins/bacon-ls.lua`. Verified headless on a scratch crate: `bacon_ls` attaches with Mason's binary and publishes diagnostics.
- `~/.cargo/config.toml` was missing and `mold` was not installed. **Fixed:** installed `mold` 3.0.0 and created the config (clang + mold linker, `profile.dev.debug = "line-tables-only"`, later changed to `debug = true`, see the Rust section). Verified: a fresh crate links with mold (`.comment` section shows it).
- Toolchain: only `stable` (rustc 1.99.0) is installed, so nightly-only tooling (`cargo miri`, `-Z` flags) needs `rustup toolchain install nightly`.
- Not installed (needed by later steps): `lazygit`, `git-delta`, `difftastic`, `perf` (all in pacman `extra`), `cargo-nextest`, `rr` (not in the pacman repos). `cargo-audit`, `cargo-watch` and Mason's `codelldb` are present.
- Unrelated config finding: nvim logs `Too many rounds of missing plugins` because `monokai-pro.nvim` is cloned from `gthelding/monokai-pro.nvim`, which 404s, and a missing `lua/plugins/theme.lua` is reported (see step 11 hygiene).

### 2. Extras and packages: done 2026-10-09
- LazyVim extras: `dap.core` (debugger front end: breakpoints, stepping, dap-ui; codelldb is already in Mason), `test.core` (neotest with rustaceanvim's adapter), `editor.overseer` (task runner), `lang.toml` / `lang.yaml` / `lang.json` / `lang.markdown` / `lang.git` (taplo for `Cargo.toml`, yamlls + SchemaStore for CI workflows). Verify names in `:LazyExtras`.
- Enable LazyVim codelens (`opts.codelens.enabled = true`) for run/debug lenses.

### 5. Safety net: done 2026-10-09

- **Local history** (`lua/config/local_history.lua`): every save (auto-save's `User AutoSaveWritePost` and manual `BufWritePost`, throttled to once a minute per repo; a save inside the window schedules one trailing snapshot at the end of the window, and one more bounded (5s) snapshot is taken on exit if a save is still unrecorded) snapshots the whole worktree, untracked files included, as a commit on `refs/lochist/<branch>` (branch name percent-encoded: `/` becomes `%2F`, so `foo` and `foo/bar` cannot collide; a detached HEAD uses `refs/lochist/%detached-<short sha>`). It uses a private index per nvim process (`.git/lochist-index.<pid>`; leftovers of dead processes are removed, the newest seeds the next one), so the real index, stash and branches are untouched and concurrent nvims do not fight over one lock; `.gitignore` and your global ignore file are respected and `target/` is always excluded (a line in `.git/info/exclude`, which also hides `target/` from the repo's `git status`; a pathspec exclude would make `git add` fail when `target/` is already ignored). Untracked files over 10 MB (`vim.g.xynovim_lochist_max_bytes`, `0` disables the cap) are skipped with one notice. `:LocalHistoryPrune [N | Nd]` keeps the newest N snapshots per branch or the last N days (default `30d`), rewrites the kept chain and runs `git gc --prune=1.hour.ago`; `:LocalHistoryPrune!` collects everything unreachable at once (also other tools' dangling commits). Unchanged trees are skipped. `:LocalHistory` / `<leader>gH` lists snapshots of the current file (not the commit that deleted it) and opens a diff against the chosen one. `:LocalHistoryRestore` picks a snapshot of the current file and replaces the buffer text (left modified and unsaved, undoable with `u`; the git index is never touched). Shell form that does not touch the index: `git restore --source=refs/lochist/<encoded-branch> --worktree -- <path>` (do not use `git checkout <ref> -- <path>`, which writes the real index). Nested git repos without commits are skipped (`git add --ignore-errors`); repos with commits are recorded as gitlinks. Old-style refs `refs/lochist/<a/b>` are renamed to the encoded form automatically, and the old shared `refs/lochist/detached` is no longer written but still shown by `:LocalHistory`. Namespace note: `refs/lochist` appears in `git log --all` and is transferred by `git push --mirror` (not by `git push`, `git push --all` or `--tags`); use `--all`/`--tags` instead of `--mirror`, or delete them with `git for-each-ref --format='delete %(refname)' refs/lochist | git update-ref --stdin`.
