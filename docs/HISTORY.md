# Build-out history

The step-by-step plan this config was built from (my wish list of features missed from the JetBrains workflow, written while using RustRover 2026.2, then eleven steps and several rounds of field testing), kept as an archive: what was done, how it was verified and what was not. The current state is described in the [README](../README.md) and [DETAILS.md](DETAILS.md); the rounds of fixes are in the [CHANGELOG](../CHANGELOG.md).

## Roadmap: the wish list

My wish list, written while using RustRover 2026.2 (researched 2026-10-08: 15 dimensions, each adversarially verified): features missed from the JetBrains workflow. The editor already did well on diagnostics latency, startup/footprint, raw rust-analyzer access and scriptability; the items below are mostly **tooling that is installed but inert** or unbound. Steps are in recommended order; each is verifiable (`:checkhealth`, a headless `nvim --headless` smoke run, or one real crate). Items marked *(unverified)* come from research that was not tested on this machine; test them before building on them.

### 3. rust-analyzer command keymaps: done 2026-10-09
`lua/config/keymaps.lua` binds the previously unbound rustaceanvim commands, buffer-local on rust-analyzer attach (scheduled so they also win over the `lang.rust` extra's own maps), under a which-key group `<leader>r` "rust":
- Refactor: `ra` refactor actions, `rv` extract variable, `rf` extract function, `rc` extract constant, `rM` extract module (visual selection only; rust-analyzer offers it for no other cursor position), `ri` inline (assists applied by title, no menu; "Inline macro" is deliberately not matched), `rs` structural search & replace (own prompt, then `:RustLsp ssr <query>`; visual keeps the selection), `rj` semantic join lines (also visual), `<A-j>` / `<A-k>` move item down/up (own `experimental/moveItem` request applied as plain text: `:RustLsp moveItem` expanded `$e` in a `macro_rules!` item as a snippet variable).
- Inspect: `rm` expand macro, `rh` / `rH` view HIR / MIR, `rS` syntax tree (JSON pretty-printed into a split), `rp` parent module, `rt` related tests, `rC` open Cargo.toml, `rd` and `rE` (both open the item's documentation: the local `rustup doc` copy when it exists, else docs.rs) (a notice instead of rustaceanvim's `URI must contain a scheme` error when an item has none), visual `rk` hover range.
- Diagnostics: `re` explains the `E0000` code of any diagnostic on the line (rust-analyzer, clippy or bacon-ls; found in `code` or the message) with `rustc --explain` in a float. rustaceanvim's `explainError`, `renderDiagnostic` and `relatedDiagnostics` accept only `source == 'rustc'` (cargo check) diagnostics, which `checkOnSave = false` never produces, so `rD` and `rr` were removed.
- Symbols: `rw` workspace symbol, `rW` workspace + dependencies, all kinds (same idea as "include non-project items" in the JetBrains IDEs); one prompt, results in the quickfix list. `vim.npcall` (removed in nvim 0.12, rustaceanvim still calls it) is shimmed to `vim.F.npcall`. Tests: `<leader>tD` runs `cargo test --doc --workspace` in a terminal (nextest cannot run doctests, so neotest reports them wrongly: a failing doctest is shown as skipped, not failed (field test 2026-10-13); use `<leader>tD`).
- Server: `rR` reload workspace, `rP` rebuild proc macros.
- `<leader>cR` is restored to a file rename in Rust buffers (the extra had shadowed it with code actions; use `<leader>ca`). The prompt is ours and refuses an existing destination (Snacks' fs rename overwrote it), then hands over to `Snacks.rename`; it is also bound through LazyVim's LSP keys (`servers["*"].keys`), which re-apply it on every capability registration. `<leader>r<key>` where nothing is bound (Cargo.toml, Lua, an unbound key in a Rust buffer) only notifies "Rust buffers only" (Vim parsed `<Space>rv` as `l` + `rv` and replaced a character).
Verified headless: all maps present and buffer-local; `<leader>rv` on `1 + 2` produced `let var_name = 1 + 2 + 3;`; `:RustLsp view hir` opens. Not exercised: the other assists, move item.

### 5. Safety net: done 2026-10-09
The JetBrains IDEs' Local History covers deleted files, `reset --hard` and AI edits; xynovim had only `undofile`, and `99` runs `claude --dangerously-skip-permissions` on top of 1s auto-save. Now:
- **Local history** (`lua/config/local_history.lua`): every save (auto-save's `User AutoSaveWritePost` and manual `BufWritePost`, throttled to once a minute per repo; a save inside the window schedules one trailing snapshot at the end of the window, and one more bounded (5s) snapshot is taken on exit if a save is still unrecorded) snapshots the whole worktree, untracked files included, as a commit on `refs/lochist/<branch>` (branch name percent-encoded: `/` becomes `%2F`, so `foo` and `foo/bar` cannot collide; a detached HEAD uses `refs/lochist/%detached-<short sha>`). It uses a private index per nvim process (`.git/lochist-index.<pid>`; leftovers of dead processes are removed, the newest seeds the next one), so the real index, stash and branches are untouched and concurrent nvims do not fight over one lock; `.gitignore` and your global ignore file are respected and `target/` is always excluded (a line in `.git/info/exclude`, which also hides `target/` from the repo's `git status`; a pathspec exclude would make `git add` fail when `target/` is already ignored). Untracked files over 10 MB (`vim.g.xynovim_lochist_max_bytes`, `0` disables the cap) are skipped with one notice. `:LocalHistoryPrune [N | Nd]` keeps the newest N snapshots per branch or the last N days (default `30d`), rewrites the kept chain and runs `git gc --prune=1.hour.ago`; `:LocalHistoryPrune!` collects everything unreachable at once (also other tools' dangling commits). Unchanged trees are skipped. `:LocalHistory` / `<leader>gH` lists snapshots of the current file (not the commit that deleted it) and opens a diff against the chosen one. `:LocalHistoryRestore` picks a snapshot of the current file, asks Restore/Cancel (a file that did not exist in that snapshot only warns), then replaces the buffer text (left modified and unsaved, undoable with `u`; the git index is never touched). Shell form that does not touch the index: `git restore --source=refs/lochist/<encoded-branch> --worktree -- <path>` (do not use `git checkout <ref> -- <path>`, which writes the real index). Nested git repos without commits are skipped (`git add --ignore-errors`); repos with commits are recorded as gitlinks. Old-style refs `refs/lochist/<a/b>` are renamed to the encoded form automatically, and the old shared `refs/lochist/detached` is no longer written but still shown by `:LocalHistory`. Namespace note: `refs/lochist` appears in `git log --all` and is transferred by `git push --mirror` (not by `git push`, `git push --all` or `--tags`); use `--all`/`--tags` instead of `--mirror`, or delete them with `git for-each-ref --format='delete %(refname)' refs/lochist | git update-ref --stdin`. Verified headless: untracked file captured and recoverable after deletion, `target/` excluded, no-change run creates nothing, real `git status` unchanged; after the field test fixes 20 further checks (nested commit-less repo, `foo` then `foo/bar`, legacy ref migration, detached HEAD, unicode paths, restore of a deleted file, `git fsck` clean), the trailing snapshot arriving at about 61s with the last save's content, and a save followed by `qa!` producing a final snapshot with nvim exiting in about 1.8s. Not verified: that `:LocalHistoryRestore` is undoable in the full config (the undotree sequence moved but the buffer text did not visibly revert in the headless run; plain `set_lines` + undo works in `nvim --clean`), the picker UI, the timer when the repo is deleted mid-run. Known limit: snapshots accumulate until you run `:LocalHistoryPrune`; `git update-ref -d refs/lochist/<branch>` resets a branch's history.
- **Undotree**: `<leader>uu` opens Neovim 0.12's built-in `nvim.undotree`.
- **`99` guard** (`lua/plugins/ninety-nine.lua`): a wrapper around the Claude provider takes a forced snapshot ("before 99 request") before every request and starts the agent only once that snapshot is finished (15 s at most; it used to start at once and a fast agent rewrote files while they were still being read), turns auto-save off while any request is in flight (so the agent's edits can be reviewed/undone before they hit disk), and runs claude inside **bubblewrap** (`lua/config/agent_sandbox.lua`). Auto-save is re-enabled only if the guard turned it off and it is still off (a user who switched it back on, or had it off, is not overridden). The in-flight counter is released exactly once per request: on `on_complete`, on a synchronous throw, and on cancel (`<leader>9x`), so cancelling restores auto-save without waiting for `on_complete`, which never comes if no process started. Sandbox:
  - Namespaces: unshares user (nested userns disabled), pid, ipc, uts and cgroup, drops all capabilities and uses `--new-session` (blocks TIOCSTI); with its own pid namespace other processes' `/proc/PID/environ` and `root` are invisible.
  - Filesystem: read-only except the project, 99's tmp dir, `~/.claude`, `~/.cache/claude`, `~/.local/state/claude` and cargo's registry, git and `.package-cache` files. `~/.local/share/claude` (the claude binary), `~/.cargo/bin` and `~/.cargo/config.toml` are read-only. If nvim was started in `$HOME` or `/`, the project is not made writable.
  - Project locks (read-only): the whole `.git` (plus the gitdir and commondir resolved from a `.git` file, plus nested `.git` up to 2 levels deep), `.gitmodules`, `.envrc`, `.mise.toml`, `.tool-versions`, `.nvim.lua`, `.nvimrc`, `.exrc`, `.vscode/tasks.json` and `settings.json`, `.cargo/config(.toml)`, `.mcp.json`, `project/.claude` and `project/.git` (both masked with an empty read-only dir when missing; bwrap leaves an empty `.claude/` and `.git/` in the project, so a later `git init` needs `rmdir .git` first: without the mask the agent ran `git init` and planted `core.fsmonitor`, which the next unsandboxed `git status` executed). Only files that exist are locked, so a missing one can still be created by the agent. **Consequence: the agent cannot `git commit` inside the sandbox**; you commit.
  - Inside `~/.claude`: `settings.json`, `settings.local.json`, `CLAUDE.md`, `keybindings.json`, `hooks`, `commands`, `agents`, `skills`, `plugins`, `output-styles`, `ide`, `chrome` and `security` (the security-guidance hook imports from `security/agent-sdk-venv` outside the sandbox: a planted `.pth` there ran with your privileges) are read-only; `projects/` is read-only except this project's own transcript directory (a bind mount cannot be renamed, so `mv projects/<name> ...; mkdir -p projects/<name>/memory` no longer works around the memory mask; other projects' transcripts are read-only, and the own directory is created if it is missing); `~/.claude` itself is created when absent (bwrap cannot make the masks' parents on the read-only root); `daemon` and `sessions` (control and session keys) are hidden. `~/.claude.json` is a private 0600 per-request copy (it holds user-scope MCP servers that would otherwise run unsandboxed); what claude writes there is discarded.
  - Hidden: `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.azure`, `~/.config/gh`, `~/.docker`, `~/.kube`, keyrings, browser profiles, mail, `.netrc`, `.npmrc`, `.pypirc`, cargo credentials, histories (`~/.*_history*`, `~/.lesshst`), winapps/freerdp/rustdesk and similar, plus `/run/docker.sock` (the user is in group docker, so it was a root-equivalent escape), `/run/docker`, `/run/containerd`, `/run/podman`, `/run/libvirt`, `/run/dbus`, `/run/snapd*.sock` and `/run/user/UID`.
  - Environment: names are scrubbed by pattern (contains TOKEN, SECRET, PASSWORD, API_KEY, CREDENTIAL, PRIVATE_KEY, ACCESS_KEY, AUTH_SOCK; PASSPHRASE, ASKPASS; prefixes AWS_, AZURE_, GOOGLE_, GCP_, GCLOUD_, DOCKER_, KUBE, GH_, GITHUB_, GITLAB_, NPM_, CARGO_REGISTR, VAULT_, OPENAI_, STRIPE_; plus `MYSQL_PWD`, `SSHPASS`, `DATABASE_URL`, `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, `DBUS_SESSION_BUS_ADDRESS`, `SSH_AUTH_SOCK`, `KUBECONFIG`). `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` are scrubbed too while `~/.claude/.credentials.json` exists (then claude uses the file login).
  - Second hardening pass (2026-10-12, from an adversarial re-review): `.cargo/` and `.vscode/` are locked as whole directories (renaming the parent no longer bypasses the file lock) and `.cargo/` is created empty and read-only when absent, also in workspace members up to depth 3 (member `.envrc` too); `~/.claude/{rules,chrome}` and `projects/*/memory` are read-only; absent `~/.claude/{hooks,commands,agents,skills,rules,output-styles}` are masked with empty read-only dirs; `shell-snapshots` and `session-env` are ephemeral tmpfs. Side effect: empty `.cargo/` dirs (and empty dirs under `~/.claude`) are left behind by the masks. Verified with 12 bash stand-in attacks; `claude --version` still runs inside.
  - Third pass (field test batch 3): the project's own `~/.claude/projects/<path with every non-alphanumeric as "-">/memory` is read-only even while it does not exist yet (it is masked with an empty read-only dir, which stays behind; before, a first agent run could plant a `MEMORY.md` that the next unsandboxed claude loads). The same mask for absent `~/.claude/{hooks,...}` now also applies when the project is `$HOME`. Verified headless as the user with bash stand-ins (a stub provider through the real guard and sandbox, and the wrapper directly): `mkdir -p memory` plus `MEMORY.md` and `other.md` writes, renaming the dir, and a symlink to its parent all blocked, while the project's session transcript path (`projects/<name>/s.jsonl`) and project files stay writable; symlinks to `~/.bashrc` and `~/.claude/settings.json` cannot be written through; `/proc/sys/vm/drop_caches`, `/proc/sysrq-trigger`, `/proc/self/root/...` and `/proc/1/root/...` writes, nested bwrap and `unshare -r` fail; only 5 pids are visible; `GITHUB_TOKEN` is unset, `.git/hooks` and `git commit` are read-only; a local TCP port on 127.0.0.1 IS reachable (documented residual), `/run/user/UID` is not (and `::1` is reachable from inside the sandbox too: the network namespace is shared). The guard through the stub provider: auto-save off while a request is in flight and on afterwards, back on after a synchronous throw, still off with two requests and one cancel, a user-disabled auto-save stays off, and the "before 99 request" snapshot exists.
  - It is still a denylist on a read-only view of the filesystem with the network open. Residual risks: `~/.claude/.credentials.json` must stay readable and writable (OAuth refresh), so an agent can read and exfiltrate that token; everything unlisted under `$HOME` is readable; loopback services and abstract sockets are reachable; cargo's `registry/src` and `git` are writable (your own cargo may later build planted code); nested `.git` deeper than 2 levels is not locked; files the project lacks (`.envrc`, `.vscode/tasks.json`, `rust-toolchain.toml`, `bacon.toml`) can be created by the agent (only `.cargo` and `.claude` are masked when absent), and secret names the pattern does not know (`STRIPE_KEY` is covered by its prefix, an arbitrary `FOO_KEY` is not) pass through; the project's source and `build.rs` are the agent's by design. Treat it as a seatbelt, not a jail. Opt out with `vim.g.xynovim_99_sandbox = false`.
  - Verified (headless, as the user, with bash stand-ins for claude): `claude --version` runs inside the sandbox with all flags (2.1.296); 49 attack probes were blocked (writes to `~/.bashrc`, `~/.profile`, autostart/systemd/cron, `.git` and hooks, project `.claude`, `~/.claude` settings/hooks/plugins, `~/.cargo/bin`, the claude binary; symlink and `/proc/self/root` tricks; mount, `unshare -r`, nested bwrap; TIOCSTI; reading `~/.ssh`, `~/.aws`, the daemon/session keys; the docker and system dbus sockets; seeing other pids); a write to `~/.claude.json` hit only the copy; `cargo build`, `test --no-run` and `clippy --offline` work inside; `git status` works, `git commit` fails with "Read-only file system"; the guard passed 13 unit checks (success, sync throw, cancel without `on_complete`, cancel then duplicate completion with 2 concurrent requests, user re-enabling or having disabled auto-save, failed status) and the real provider path with a bash stand-in produced a `bwrap ... claude` command with `GITHUB_TOKEN` unset. **Not verified:** a real `99` request end to end (a live `claude` run was not permitted), so claude's own writes inside the sandbox are untested. Try `<leader>9v` once. If a request fails: first check the hidden `~/.claude/daemon` and `~/.claude/sessions` and the `~/.claude.json` copy (claude may write that file atomically via a temp file in the read-only `$HOME`), and if claude complains about a path, add it to `WRITABLE` in `agent_sandbox.lua`.
- Local history hardening: a forced snapshot (the 99 guard's) that finds another snapshot running is retried instead of dropped, a hung git is given up on after 30s so history is not disabled until restart, and a failed `update-ref` warns and no longer counts as a snapshot. The 99 guard also restores auto-save if `make_request` throws synchronously. `lua/plugins/gitsigns.lua` sets `attach_to_untracked = true`, so signs also show in untracked files, for example in a repo with no commits yet (verified: 3 sign extmarks on an untracked file in an empty repo, 0 without the override). Known, not changed: snapshots include untracked files such as `.env`.
- Local history, field test batch 3: a save followed by an immediate quit now also snapshots when the first snapshot of the session is still in flight (VimLeavePre kills its git and redoes it synchronously, 5s budget); `last` (the throttle) is only set after a snapshot succeeded, a failure backs off 10s and retries once; the ref moves with a compare-and-swap and is re-read on a lock or mismatch (up to 10 jittered attempts), a stale own `index.lock` is removed, a ref lock older than 60s is removed, and a lasting lock error notifies once; the 30s watchdog kills the git child; untracked files over the size cap are excluded from `git add` and dropped from the private index when they grew past it. A linked worktree works (snapshot on its own `wtb` ref, index file in the worktree's gitdir, shared `info/exclude`).

### 6. Git depth: done 2026-10-09
- **diffview.nvim** (`lua/plugins/diffview.lua`): `<leader>gv` working tree / merge conflicts (3-way), `<leader>gV` branch vs `origin/HEAD` (falls back to `origin/main`, `origin/master`, then says so instead of showing a raw git error), `<leader>gF` file history (visual: selection history), `<leader>gq` close. - **mergiraf** (pacman) as a syntax-aware merge driver for `*.rs` (registered in global git config, attributes in `~/.config/git/attributes`). Verified: two branches adding different `use` lines at the same spot merged cleanly into a sorted-by-intent result with no conflict markers. `Cargo.lock` conflicts are not handled (a regenerate-on-conflict driver was only a sketch; untested).
- Global git config (user `xynorash`, `~/.gitconfig`): `merge.conflictstyle = zdiff3`, `rerere.enabled` + `rerere.autoUpdate`, `rebase.autoSquash`, `rebase.updateRefs`; aliases `git dft` / `git dlog` (difftastic, structural diff that ignores rustfmt-only churn; deliberately an alias, not a global `diff.external`, so lazygit/gitsigns keep parsing plain diffs).

- **Per-repo opt-ins, not applied automatically:**
  - Ignore formatter-only commits in blame: list the commit hashes in `.git-blame-ignore-revs` and run `git config blame.ignoreRevsFile .git-blame-ignore-revs` (gitsigns blame honours it).
  - Pre-commit hooks (lefthook is not in the official Arch repos: install it with `go install github.com/evilmartians/lefthook@latest`, or use a plain `.githooks/pre-commit` script). Example `lefthook.yml`; keep a separate `CARGO_TARGET_DIR` so hooks never contend with the editor's builds, and never make hooks depend on a running LSP:
    ```yaml
    pre-commit:
    ```

### 8. Context switcher: done 2026-10-09
`lang.rust` sets `allFeatures = true` and bacon-ls used a hardcoded `--all-features`, so mutually exclusive features (ssr/csr, std/no_std) gave bogus errors, and there was no target switcher. Now both diagnostic tiers follow one per-project choice:
