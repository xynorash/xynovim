## Limits (not measured, or only partly)

- Linux only (reads `/proc`); one machine, one run of this script; load average at start is above.
- Startup is measured in a tmux pty: it includes exec and the terminal protocol handshake of nvim, but not the terminal emulator's own time to first paint.
- The demo crate has two source files. Memory, indexing time and clippy time on a large workspace are not covered.
- A diagnostic cell reads `none` when no matching diagnostic arrived within 20 s; it does not say the config could not be set up to produce one.
- Large-file numbers are for a file outside a Cargo crate, generated by the harness.

## Was the machine quiet? No.

Load average at the start of the run was 0.79 (1-minute), so the check on `uptime` passed, but the machine was not quiet: another session of the user compiled and ran a Rust program on one core for most of the day, six processes sat in disk wait (about 35 % iowait in `vmstat`), 4.4 GB of swap were in use, Steam and Discord were running. I waited five minutes between runs (the 1-minute load was 2.3 after the first wait, 0.9 after the second) and took the final run at a load of 0.8. The raw numbers are therefore 10 to 25 % slower than `baseline.json` (taken on a quieter day), and the way to read them is the paired runs below, which alternate the old and the new code in the same minutes. A quiet-machine repeat is open (command in `docs/PROGRESS.md` section 5).

## What the integration run found and fixed

An earlier paired set (baseline, `85db1a3` and this checkout) showed the no-file start 2 to 4 ms slower than both (36.9, 38.7 and 40.4 ms medians). Cause, found with `--startuptime`: the code-lens deprecation shim added by the warnings sweep touched `vim.lsp.codelens` from `lua/config/lazy.lua`, which loads `vim.lsp` and its submodules before the first screen (2.3 ms). Removing the shim brought the start back to the old code's (33.7 against 33.6 ms), and the shim now lives in `nvim-lspconfig`'s opts (commit `5500643`), with a spec that fails when `vim.lsp.codelens` is loaded at start (checked by putting the access back: it fails) and one that the key and a direct call do not reach `vim.deprecate`. After the fix, no file: 37.6, 39.0, 38.1 ms against 37.7, 35.5, 38.3 ms for the baseline code in the same minutes (no difference beyond the spread).

## What is slower, and what is not explained

- **Edit to the first rust-analyzer diagnostic is slower than the baseline code by a few milliseconds.** Paired medians of five trials, in four paired sets: baseline 27.0, 27.7, 27.6 | 34.9, 34.0, 30.6 | 29.4, 29.9, 30.5 | 34.5, 42.5, 38.1; this checkout 35.8, 32.6, 36.3 | 38.6, 35.7, 29.6 | 36.4, 37.1, 40.1 | 44.9, 49.4, 46.3. That is -1 to +10 ms on 27 to 42 ms; the spread of single trials is 24 to 46 ms in one run (28 to 46 ms in `final-2026-11c`). I tried to isolate it: with the rainbow boot module removed there was no recovery; with the rainbow boot and the bacon-ls duplicate filter removed together about 5 of the 7 ms came back in one set (32 to 34 ms); with the duplicate filter removed alone it did not. Cause not isolated, not fixed. The 2026-11-13 earlier paired set ([final-2026-11c.md](final-2026-11c.md)) put the rainbow redraw at +1 to +3 ms. It stays an open item: edit-to-diagnostic is about 35 ms here against 27 for the old code, below anything a person notices, but it is a regression of this metric and I am not calling it none.
- **Edit to the first clippy diagnostic**: 570 to 580 ms in all sets for both, +0 to +10 ms new, inside the spread.
- **Resident memory of Neovim itself right after start is 3 MB higher** (28.7 against 25.7 MB after `VeryLazy`, headless): the modules of the UI, hint, trust and rainbow work (`config.ui`, `config.ui_chrome`, `config.eolhints`, `config.rainbow*`, `config.workspace_trust`, `xynovim.trust_fallback`, ...) load after the first screen. Rainbow off (the boot call removed) left the 3 MB in place, so it is mostly the other modules. Total idle memory with rust-analyzer is 116 to 197 MB lower than the old code's because of the allocator cap, so the net is better.
