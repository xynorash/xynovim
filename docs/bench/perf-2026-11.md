# Performance work, 2026-11-12

Measured with `scripts/bench` (see `scripts/bench/README.md`) on the machine of `baseline.json` (Ryzen 7 5800X, 16 CPUs, NVIM v0.12.6, rust-analyzer 1.99.1). Raw data: `perf-2026-11.json` (medians and samples), a full run of the final tree: `perf-2026-11-after.json` / `perf-2026-11-after.md`. Other processes shared the machine (1-minute load 1.4 to 4.0), so "before" (git HEAD in a scratch copy) and "after" (this tree) were run **alternately**, not one block after the other. Numbers are medians of the runs listed; the baseline of `baseline.json` could be reproduced (40k lines: stall 629 ms here, 527 ms there).

## 1. Large file: where the time went

LuaJIT's sampling profiler (`jit.profile`, 1 ms) over the 5 s after opening a 40 000-line file, and switching one feature off at a time (`BENCH_PRE=<lua>` in `probe.lua`):

- **Memory** is not the file: with rust-analyzer stopped the whole process tree is 110 MB. rust-analyzer in detached-file mode (a file outside a crate) loads the sysroot: 640-730 MB, and +150 MB while the file is scrolled and edited. Nothing to fix in the editor; the arena cap below takes about 100 MB of it.
- **Stall**: treesitter folds (`LazyVim.treesitter.foldexpr()` is a Lua call per buffer line, plus the fold query over the whole tree), the nvim-treesitter indent query on every `o`, whole-file semantic tokens and inlay hints, and then the **injection query**: a 40 000-line file with 2 800 macro calls is 2 800 nested Rust trees that are searched on every parse. With the folds, indent, hints and tokens off the stall went 630 -> 350 ms; creating the parser without the injection query of its own language took it to 125 ms.
- Not the cause: treesitter highlighting itself (it is viewport based and async), illuminate, indent guides, treesitter-context (each < 20 ms in the experiments).

Fix: `lua/config/largefile.lua`, progressive and per buffer. Tier 1 (>= 20 000 lines, >= 512 KB, or an average line >= 300 bytes) switches off folds, treesitter indent, semantic tokens, inlay hints, code lens, spell, indent guides, word illumination, the breadcrumb, and the nested-language injections of that buffer. Highlighting, diagnostics, completion, hover and go-to-definition stay. Tier 2 is snacks.nvim's bigfile as before. `:LargeFile` shows the tier, `:LargeFile off` brings the features of one buffer back, `vim.g.xynovim_largefile = { lines =, bytes =, avg_line = }` or `false` changes or disables it. Cost: macro arguments and sqlx strings of a tier-1 buffer lose their nested highlighting. A buffer that **grows** past a limit while editing is only shed on the next write (a 25 000-line paste into a Rust buffer took 273 s in the spec before the folds were avoided; the spec now uses a plain file).

## 2. Startup with a .rs file

`--startuptime` plus the sampling profiler: from 58 ms (config loaded) to 184 ms (main loop) the log has a single 79 ms stretch of Lua with no sourced file. Inside it, measured in isolation (`vim.treesitter.query.parse`, first use in the process): Rust `highlights.scm` 36 ms, the injection queries 15 ms (nvim-treesitter's copy) and 8 ms (our sqlx extension), folds and indents 5 ms each. That is `ts_query_new` in C, memoised afterwards; every Neovim configuration pays it on the first Rust buffer, so it is a floor, not something this config can skip without losing first-paint highlighting.

What could be moved: `rustaceanvim` no longer has `nvim-dap` as a hard dependency (which ran nvim-dap, dap-ui, virtual text, mason-nvim-dap and overseer before the first paint). The `dap` module alone is required when rustaceanvim loads (the `debugSingle` capability needs it), the plugin proper loads on VeryLazy, and every dap key still loads it through lazy.nvim. Gain: 6 ms UIEnter, 14 ms fully loaded. Tried and dropped: deferring mason's registry refresh (profile said 25 ms, A/B said 0 +- 3 ms: the profiler overstated it).

## 4. Clippy latency

Edit to first bacon-ls diagnostic = debounce + 70 ms. Of the 70 ms, 44 ms is `cargo`'s own start-up with nothing to compile (measured with 20 runs of the bacon-ls command line in a copy of the crate: 44 ms no-op, 107 ms with a touched file). `--frozen`, `CARGO_INCREMENTAL=0/1`, `CARGO_BUILD_JOBS=2`, `--message-format=short`, `-q` all gave 107-126 ms; only dropping the bin target (`--lib`) gave 75 ms, which would drop diagnostics of `main.rs`. The shadow workspace is not the bottleneck; the debounce is.

| debounce | edit -> diagnostic | clippy runs for 40 keystrokes at gaps of 300 / 150 / 80 ms |
| --- | --- | --- |
| 500 ms (kept) | 570 ms | 1 / 1 / 1 |
| 250 ms | 320 ms | 32 / 1 / 1 |
| 150 ms | 220 ms | 40 / 21 / 2 |
| 80 ms | 152 ms | 40 / 40 / 26 |

A run costs 70 ms on this 2-file crate but seconds on a big workspace, so the default stays at 500 ms; `vim.g.xynovim_clippy_debounce_ms` (e.g. 250) trades runs for latency. New opt-in metric: `scripts/bench/bench.sh --only typing --type-gaps 80,150,300`.

## 5. Cold `root()`

Callers: `bacon-ls.lua` `root_dir` (now `rust_context.root_async`; falls back to the synchronous call when the installed xyno-rust.nvim has no `root_async`), `before_init` (uses `config.root_dir`, which already is the answer), `rustaceanvim.lua` settings (kept synchronous: `nowait` there returned the file-system root before cargo's answer and the live `rust-context` spec hung, so it stays correct and costs one `cargo locate-project`), `coverage.lua` / `dap.lua` (on demand, user-initiated). **Needs the user**: the `lazy-lock.json` pin of xyno-rust.nvim predates `root_async`; the effect is only active after pushing `~/projects/xyno-plugins/xyno-rust.nvim` (dev) and updating the lock, or with `XYNOVIM_DEV_PLUGINS=~/projects/xyno-plugins` (measured and spec-tested that way).

## Honest comparison with published numbers

Published like-for-like figures do not exist for most of these (retrieved 2026-11-12; see also `docs/comparison/notes.md`):

- **rust-analyzer memory**: no published figure for a small crate was found. Reports are for big workspaces: 2.5 GB usual / 4.7 GB after an update on a company repository (users.rust-lang.org, Oct 2020, https://users.rust-lang.org/t/rust-analyzer-ram-consumption/50420), 12 GB idle on the Zed codebase (https://github.com/rust-lang/rust-analyzer/discussions/20871), 13 GiB on a ~830-dependency workspace (https://users.rust-lang.org/t/rust-analyzer-using-13-gib/133914). VS Code, Zed, Helix and the Neovim configs run the same rust-analyzer binary, so this config's 702 MB (netwatch, 1 dependency) is dominated by the sysroot every client pays; **it is not shown to be ahead or behind** of any of them, only that it dropped by 123 MB and that the arena cap is not something the other starters set. The Zed/VS Code idle-memory figures in `notes.md` (142 MB vs 730 MB) do not say whether rust-analyzer is included, so they are not compared.
- **Startup**: the one published Neovim figure found is 67.4 ms +- 1.0 (`hyperfine "nvim --headless +qa"`, a personal lazy.nvim config, hardware not stated; https://aliquote.org/post/lazy-nvim/); NvChad's README says 20-70 ms. This config: 35 ms UIEnter / 64 ms fully loaded without a file (TUI in a tmux pty, a different and stricter method). **Not behind** on the published numbers, but the methods differ, so "ahead" is not claimed. With a Rust file open: 186 ms UIEnter; no competitor publishes this number, and the dominant 60 ms is tree-sitter query compilation that all of them pay. LazyVim's startuptime page (https://lazyvim.org/extras/util/startuptime) gives no number. Zed's 0.4 s / VS Code's 0.6-1.3 s are secondary-source claims (notes.md section 3); this config opens the file and shows it highlighted in under 0.2 s, a lower number than those claims, but they measure window-to-ready of a GUI, not a TUI start, so no "ahead" is claimed.
- **Large file**: no published comparable (stall after opening a 40k-line Rust file). Not comparable, so nothing is claimed; the before/after above is the only evidence.
- **Clippy latency**: VS Code, Zed and the rust-analyzer defaults run clippy on save (`checkOnSave`, a `cargo clippy` of the workspace, seconds on a real crate); this config shows clippy diagnostics 570 ms after the keystroke without saving, and 320 ms with the documented knob. Ahead on the mechanism; no like-for-like published number.
- **Still behind (honestly)**: nothing was measured to be behind a published number; what is *not* better than a typical setup: rust-analyzer's RSS is the same sysroot-dominated figure as everywhere, the first Rust file pays 60 ms of query compilation like every config, and `scripts/bench/compare.sh` (the other starters on this machine) was not run (a permission check blocked running third-party starter configs; it is left for the user).
