## Limits (not measured, or only partly)

- Linux only (reads `/proc`); one machine, one run of this script; load average at start is above.
- Startup is measured in a tmux pty: it includes exec and the terminal protocol handshake of nvim, but not the terminal emulator's own time to first paint.
- The demo crate has two source files. Memory, indexing time and clippy time on a large workspace are not covered.
- A diagnostic cell reads `none` when no matching diagnostic arrived within 20 s; it does not say the config could not be set up to produce one.
- Large-file numbers are for a file outside a Cargo crate, generated by the harness.

## Comparison with `baseline.json` and `final-2026-11.json` (2026-11-12, evening re-run)

**Read this first: the machine was busy.** This run happened while a Wine game (`wwm.exe`, 350 % CPU, 5.5 GB) and Discord ran on the same machine, load average 7 to 9 on 16 logical CPUs, swap in use. Every CPU-bound number is therefore 40 to 60 % slower than in `final-2026-11.md` (a quiet machine); memory numbers are not affected by load and match it to within 1 MB. So the table below does NOT compare this file's raw timings with the quiet-machine ones. The regression check that counts is the paired one: the previous benchmarked commit `85db1a3` (extracted with `git archive` into a scratch directory, same harness, same demo crate, same pinned plugins) and the current `dev` checkout, alternated, three runs of the startup probe and two of the large-file probe, within minutes of each other, under the same load.

Result: **no regression** (same values within the spread of the repeated runs; the one slower page-down value, 514 against 407 to 429, is inside the noise of a loaded machine and the other current run is the faster of the pair). Memory, which load does not move: idle RSS 805.5 MB against 804.5 (`final-2026-11`) and 1002.0 (`baseline`): the 197 MB saving of `MALLOC_ARENA_MAX=2` stays. Clippy first diagnostic 608 / 600 ms (type / save) against 565 / 563 on the quiet machine, same 5 of 5 trials.

**What the first re-run of this file found, and what was fixed:** run with the pinned plugins the harness measured a configuration the user would not have: the harness copies the demo crate to a temp directory with a fresh state directory, which the workspace trust gate of this branch treats as an untrusted workspace (and, because `lazy-lock.json` still pins an xyno-rust.nvim without a trust list, fails closed). rust-analyzer then started restricted (no proc-macro helper process, idle RSS 755 MB in total instead of 805 MB), bacon-ls did not start and the clippy rows read "no diagnostic within 20000 ms". That is the gate working as designed, not a slowdown, but it made the benchmark meaningless; `scripts/bench/hook.lua` now switches the gate off (`vim.g.xynovim_workspace_trust = false`, which is what a trusted workspace gets) unless `BENCH_TRUST=0`. The numbers above are from the run with the fix.

Not measured: the plugin `dev` branches (`XYNOVIM_DEV_PLUGINS`), a quiet-machine repeat of this file (ask for it when the machine is idle: `scripts/bench/bench.sh --out docs/bench/final-2026-11c.json`), other editors.
