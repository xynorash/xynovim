# Final benchmark, integration round 2026-11-13 (`final-2026-11c`)

Raw data: `final-2026-11c.json` (the whole `scripts/bench/bench.sh` run, 10 startups, 5 diagnostic trials, 40 000 and 100 000 line files).

**The machine was not quiet.** Load average at the start 3.71 4.11 3.50; during the run another session of the user compiled and ran a Rust program (about one core), Discord and a browser ran, CPU governor `powersave` (as in `baseline` and `final-2026-11`; `final-2026-11b` was `performance`). I waited about ten minutes for a quiet moment and none came, so this run is not comparable one to one with `baseline.json` (load 0.18) and `final-2026-11.json` (load 0.63).

Read as a raw number against the two quiet runs this is 10 to 15 % slower. That is the load, not the code, and the way to tell is a paired run in the same conditions: the code of `final-2026-11` (commit 85db1a3, extracted with `git archive`, the same installed plugins) against this checkout, alternating, three rounds of the startup metrics (`--only startup -n 10`), medians per round:

| | old (85db1a3) | new (62903ae + docs) |
|---|---|---|
| no file, `NVIM STARTED` | 40.5, 39.3, 39.6 | 39.8, 38.7, 38.4 |
| no file, ready | 78.4, 74.4, 75.2 | 79.9, 78.1, 76.5 |
| `.rs` file, `UIEnter` | 211.7, 198.9, 202.7 | 209.5, 199.7, 202.3 |
| `.rs` file, ready | 331.2, 311.0, 322.2 | 333.0, 318.9, 322.4 |

Same conditions, no difference in start-up (the old code measured 39.5 ms here against 33.5 ms in its own quiet run: the load costs about 6 ms and 28 ms, which is the whole gap above). Large-file open, two paired rounds: 147 / 149 ms old, 146 / 150 ms new (40 000 lines), 69 / 65 ms against 62 / 66 ms (100 000 lines); RSS after the operations 119 MB in all four for the 100 000-line file and 840 / 874 MB new against 859 / 814 MB old for the 40 000-line one.

Edit to first diagnostic is the one metric where the new code is slower in the paired runs, and it is small: three paired rounds of five trials each, medians of the type-error trials 33.5 ms old, 34.5 ms with the rainbow brackets switched off (`enabled = false` in a scratch copy) and 36.2 ms new, against a spread of 28 to 46 ms between single trials; bacon-ls 571 ms old, 573 ms new. The 1 to 3 ms is what the rainbow brackets cost per redraw (`docs/RAINBOW.md`, measured +1.1 to +2.4 ms), and the diagnostic is only seen after a redraw in this harness. It is within the noise of this load, it is not a regression of start-up, memory or the large-file paths, and I did not remove anything to hide it. A quiet-machine rerun (`scripts/bench/bench.sh --out docs/bench/final-quiet.json`) is yours if you want the clean number.

## Limits (not measured, or only partly)

- Linux only (reads `/proc`); one machine, one run of this script; load average at start is above.
- Startup is measured in a tmux pty: it includes exec and the terminal protocol handshake of nvim, but not the terminal emulator's own time to first paint.
- The demo crate has two source files. Memory, indexing time and clippy time on a large workspace are not covered.
- A diagnostic cell reads `none` when no matching diagnostic arrived within 20 s; it does not say the config could not be set up to produce one.
- Large-file numbers are for a file outside a Cargo crate, generated by the harness.
