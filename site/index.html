A personal Neovim configuration for Rust, built on LazyVim and inspired by JetBrains' tools. Instant diagnostics, a debugger and test UI, a git safety net, and a test suite you can run yourself.

What you get

Why xynovim

Built on LazyVim, developed on Linux (Arch) and also run in CI on Windows and macOS (see Platforms), with the Island Dark colour scheme generated from the author’s own colour-scheme export. Everything on this page was recorded from the real config running on the small demo crate: nothing is mocked up.

  • Two diagnostic tiers: rust-analyzer answers while you type, clippy follows about half a second later, on every keystroke and before any save.

  • A debugger and a test runner that look like the ones in an IDE: breakpoints with Rust-aware variable views, a test summary tree, coverage in the gutter.

  • A safety net: every save is snapshotted as a git ref (a “Local History”), and the AI agent runs inside a sandbox.

  • Treesitter everywhere: sticky scope, text objects, SQL injected into sqlx strings, a live syntax-tree view.

  • Tested: {{TESTS}} passing checks across {{SPECS}} spec files, one per feature area, runnable with one command after a clone (below).

01 diagnostics

Two-tier diagnostics

rust-analyzer’s own diagnostics appear as you type (type errors in about 0.01 to 0.15 s). bacon-ls runs clippy against a hardlinked shadow of your workspace on every buffer change (about 0.56 s median), so lints show up before you save. Each message shows its first line plus the source; the full text is one <leader>cd away.

  • <leader>cd
02 treesitter

Treesitter, visibly

Treesitter drives the highlighting, the sticky scope at the top of the window (the for / match / arm headers you have scrolled past stay pinned), the text objects and the sqlx SQL injection. Two built-in views make it concrete: :Inspect and :InspectTree.

vaf selects a whole function through the treesitter text objects.

  • :Inspect
  • :InspectTree
  • vaf
03 refactoring

Refactoring and rust-analyzer commands

Every rust-analyzer command rustaceanvim offers has a key under <leader>r, discoverable through which-key: extract variable / function / constant / module, inline, structural search and replace, semantic join lines, move item, expand macro, view HIR / MIR, explain error code, workspace symbol including dependencies, go to super method, and more.

  • <leader>rv
  • <leader>rf
  • <leader>rc
  • <leader>ri
  • <leader>rs

Tests and coverage

neotest with the rustaceanvim adapter and cargo-nextest: a summary tree with per-test results, and line coverage from cargo-llvm-cov shown in the gutter.

05 debugging

Debugging

nvim-dap with codelldb, a dap-ui layout sized for Rust’s long type names, and lldb’s Rust formatters loaded automatically (a String shows as text and a struct as {host:"127.0.0.1", ...}, not as raw memory). <leader>db sets a breakpoint, <leader>dR lists every debuggable target of the workspace, and a panic stops at the panicking frame.

  • <leader>db
  • <leader>dc
  • <leader>dr
  • <leader>dR
  • <leader>du
06 features and target

One feature set for both tiers: :RustContext

Cargo features and the build target are chosen per project and applied to both rust-analyzer and bacon-ls, so the two tiers never disagree. In the demo ssr and csr are mutually exclusive: with all features on, both tiers report the conflict; choosing only ssr makes it go away in both.

The choice is stored per workspace and survives restarts. :RustTargets lists every bin / example / test / bench with run, test, build, profile and flamegraph actions; :RustTools covers cargo-deny, audit, machete, bloat and build timings.

  • :RustContext
  • :RustTargets
  • :RustTools
  • <leader>rF
  • <leader>rX
07 git

Git, and a safety net

lazygit (with delta), diffview for diffs, merge conflicts and file history, mergiraf as a syntax-aware merge driver, and Local History: every save (manual or auto-save, throttled) also writes the whole worktree, untracked files included, as a commit under refs/lochist/ using a private index. Deleted files and git reset --hard become recoverable without touching your real index, stash or branches.

:LocalHistory browses and diffs, :LocalHistoryRestore restores, :LocalHistoryPrune cleans up.

  • <leader>gg
  • <leader>gv
  • <leader>gH
  • :LocalHistory
08 theme

Island Dark

The colour scheme is generated from the author’s own colour-scheme export, which is not distributed (the generated palette is lua/island/palette.lua), by tools/icls2nvim.py, which converts a scheme file you supply yourself: colours, italics, underlines and the org.rust.* entries that colour structs, enums, macros and lifetimes. Contrast was checked against WCAG targets and lifted where the export was too dim. Floats and the completion menu stay solid on a transparent editor (<leader>uO toggles the editor background).

09 macros and dependencies

Macros and dependencies

Adding a crate used to leave its macros and features half used: no completion inside #[serde(, no use for a crate that is not a dependency yet, a missing derive feature that nothing pointed at, a stale cannot find crate error after cargo add. Everything runs in nvim on top of rust-analyzer, cargo and treesitter; no extra language server.

Attribute completion is data driven: one JSON file per crate in data/macro_attrs/ (serde, clap, thiserror, tokio, strum, derive_more, sqlx, utoipa, schemars, bon), and a project can add its own in .xynovim/macro_attrs/.

add a crate

Adding a crate that is no dependency yet

uuid::Uuid::new_v4() without uuid in Cargo.toml: the code action offers “Add crate uuid”, the picker lists the crates.io results and the features of the chosen release (here v4 toggled on), the target package is asked, then cargo add runs and the error goes away without waiting. Typing Uuid afterwards asks to import it.

  • <leader>rA
  • :CrateAdd
  • :CrateFeatures
  • <leader>rI
attributes and derives

The missing feature, derive and attribute completion

serde without its derive feature gives cannot find derive macro Serialize; <leader>rG enables the feature in Cargo.toml. #[derive(Des completes derive names with docs and adds the use on accept; #[serde( and #[arg( offer keys with their docs, and rename_all = " offers its values.

  • <leader>rG
  • #[serde(
  • #[arg(
  • #[derive(
imports and macros

Ranked imports, macro expansion and signature help

Error exists in std, std::io, std::fmt and clap: <leader>rI ranks them with the reasons; the pick is remembered, so the next file offers it as the single import. <leader>rx shows the expansion of a derive, gi lists what it generated, and <C-k> shows the matcher arms of a macro_rules! call (the arm that fits the arguments typed so far is highlighted).

  • <leader>rI
  • <leader>rO
  • <leader>rx
  • <C-k>
10 new projects

New projects

Start an egui app, a binary, a library or a workspace from the dashboard or a command, with the prompts, the name rules and the failure cleanup done for you.

egui

New egui project

The dashboard has a New egui Project entry (e) and there is the command :EguiNew [name]. Both follow the steps of emilk/eframe_template against the current template: the ZIP of its main branch is downloaded every time (never a copy kept in this config) and personalised, so a new egui or eframe release of the template is picked up without touching the config.

It asks for the project name, author name and e-mail (prefilled from git config) and the parent directory; the template’s toolchain pin is not copied, so your own Rust is used.

  • :EguiNew
  • dashboard e
binary, library, workspace

New Rust binary, library and workspace

Three entries on the dashboard, New Rust Binary (b), New Rust Library (i) and New Rust Workspace (w), and the commands :RustNewBin, :RustNewLib, :RustNewWorkspace and :RustNewMember.

A binary or library is cargo new --vcs git in a chosen parent directory. A workspace has no one-step cargo command, so it is built here: a root Cargo.toml with members = ["crates/*"], [workspace.package] and an empty [workspace.dependencies], a first member that inherits version and edition, and git init -b main. :RustNewMember adds a member to the workspace of the current buffer.

  • :RustNewBin
  • :RustNewLib
  • :RustNewWorkspace
  • :RustNewMember
11 agent

The AI agent, sandboxed

99 with the Claude Code provider is wired in (<leader>9), and its claude --dangerously-skip-permissions runs inside bubblewrap, which exists only on Linux, so the agent only runs where a sandbox exists (Linux with bwrap); without one, 99 refuses to start a request unless you opt out explicitly (vim.g.xynovim_99_sandbox = false, or vim.g.xynovim_99_allow_unsandboxed = true when there is no sandbox backend), and every unsandboxed request warns. Where bwrap works: the filesystem is read-only except the project and Claude’s own state, credentials and agent sockets are hidden, .git/hooks, .git/config and Claude’s settings are locked read-only, the environment is scrubbed of tokens, and every request is preceded by a Local History snapshot with auto-save paused. It is a seatbelt, not a jail: the network stays open (details in docs/DETAILS.md). There are no screenshots: the sandbox has no UI, and a real request needs an account.

Run them yourself

Tested

The config ships with an automated suite. Each spec file runs in its own headless Neovim with the full config and a hard timeout, so a hanging test cannot stall the rest.

  • {{SPECS}}spec files
  • {{TESTS}}checks passing
  • {{SKIPPED}}skipped with a stated reason
  • {{FAILED}}failing
scripts/test.sh                  # everything (or: make test)
scripts/test.sh routes smoke     # only spec files whose path contains one of the words
scripts/test.sh --list           # the spec files, nothing run
scripts/test.sh --coverage       # also a per-file line-coverage report
  • Nothing of yours is touched: the specs run against a temp config / state / cache. Missing tools (rust-analyzer, tmux, bubblewrap, lazygit, ...) make their specs skip with a message, never fail.
  • One spec per feature area: tests/COVERAGE.md maps every feature to the spec that tests it and lists what has no test and why.
  • CI: the ci workflow bootstraps the plugins on their locked commits, runs a startup smoke test and the whole suite on a clean Ubuntu machine for every push.
  • How the harness works and how to write a spec: docs/TESTING.md.

Get it

Install

Two commands. scripts/bootstrap.sh checks the prerequisites it needs and prints what is missing; :checkhealth xynovim checks the rest later, with what each one is for.

git clone https://github.com/xynorash/xynovim ~/.config/nvim   # or ln -s <checkout> ~/.config/nvim
~/.config/nvim/scripts/bootstrap.sh

A plain nvim --headless '+Lazy! restore' +qa on an empty plugin directory makes lazy.nvim install in several rounds and rewrite lazy-lock.json after every one, so the pins of the plugins found later are dropped and those land on their newest commit. The script runs Lazy! install, puts the original lockfile back, runs Lazy! restore and fails if lazy-lock.json differs afterwards; CI runs it too.

Full prerequisites and details in the README

Prerequisites, in short

  • To bring the config up: nvim 0.12, git, curl, tar, unzip, gzip, gcc, the tree-sitter CLI, node and npm.
  • For the Rust workflow: cargo, rustup (with the stable toolchain, its clippy and llvm-tools components) and rust-analyzer on PATH.
  • Installed by Mason: bacon-ls, codelldb, taplo, marksman, lua-language-server, stylua and the other language servers and tools.
  • Optional, each one only costs its feature: mold + clang, cargo-nextest, cargo-deny, cargo-expand, lazygit, delta, bwrap (the 99 sandbox, Linux only; without it 99 refuses to run).

Platforms

The shell scripts are bash conveniences for Linux and macOS, with PowerShell counterparts for Windows (scripts/bootstrap.ps1). The config itself is Lua and is meant to run wherever Neovim 0.12 runs with the prerequisites. What CI shows, and no more:

  • Linux: developed on (Arch), fully tested. Ubuntu ci run 39673715029: 1724 passed, 0 failed, 76 skipped.
  • Windows: the plugin restore from the lockfile, a silent headless start and the specs that are not Linux-only pass. platforms run 39673715062: 1077 passed, 0 failed, 87 skipped; 10 of the 38 spec files are skipped whole there and not demonstrated. Green in 5 of the 6 runs from 39660597368 on (the one red run was a spec path assertion, fixed afterwards).
  • macOS: not reliably green. Neovim starts and most specs pass, but the job did not pass in 4 of the 5 runs that finished from 39660597368 on (green once: run 39663956677, 1431 passed, 0 failed, 73 skipped).
  • Linux only by design: the 99 agent sandbox (bubblewrap; without it 99 refuses to run), the remote clipboard, the tmux-based and bash-stub test tooling (scripts/test.sh) and the mold linker setup.
  • Not demonstrated on Windows or macOS: Local History, startup options, new Rust and egui project creation, live rust-analyzer flows on Windows, and debugging through codelldb. docs/KNOWN_ISSUES.md has the list.

Honest edges

Known limitations

  • Neovim 0.12; developed on Linux. Windows is exercised in CI and macOS is not reliably green (Platforms). The previous from-scratch Windows config lives on the windows-legacy branch.
  • The agent sandbox is a seatbelt, not a jail. The network stays open, and no real request to the agent was driven in the test suite.
  • The macros and dependencies work is tested headless. The suite uses real cargo and rust-analyzer, but the pickers and key presses were not driven in a real terminal; the unknown-crate hint is deliberately conservative (a miss is better than a false hint), and a “(guess)” import can miss.
  • Two Neovim instances on the same workspace share bacon-ls’s shadow, so one’s unsaved text can show up as clippy errors in the other (upstream; open one Neovim per workspace). A multi-file rename is undone per buffer: use <leader>gH local history to revert it.

The complete list, with what was decided and why: docs/KNOWN_ISSUES.md.

Learn the workflows

Guides

Six short guides to the parts of the configuration people ask about most: what each one does, the keys, why it is set up that way and where it stops.

  • Rust diagnosticsHow xynovim gets Rust errors on screen while you type: rust-analyzer for instant type errors, clippy through bacon-ls half a second later, before any save.
  • Rust debuggingSet breakpoints, read Rust values and stop at panics in Neovim: the nvim-dap and codelldb setup of xynovim, with the debuginfo setting that makes locals work.
  • Tests and coverageRun Rust tests from Neovim with neotest and cargo-nextest, read a summary tree, and see line coverage from cargo-llvm-cov in the gutter, on demand.
  • Workspaces, features, cratesCreate Rust binaries, libraries and workspaces, add crates with their features and fix missing derive features from Neovim: :CrateAdd, :CrateFeatures and more.
  • Git safety netEvery save in Neovim written as a git ref you can restore, plus lazygit and diffview: how xynovim recovers deleted files and edits that undo cannot bring back.
  • Island Dark themeIsland Dark is the dark colour scheme of xynovim: a generated palette mapped to Treesitter captures, LSP tokens and the plugins in use, tuned for contrast.
